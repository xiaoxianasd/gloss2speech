# W1 验收清单与实测方法（端侧快路径）

> 说明：该清单针对 `research/fastpath-frontend/` 的端侧 DTW 原型；当前产品按《工程实现方案》实现，
> 本清单保留作为后续可选优化（若重新启用端侧识别）的参考。

> 适用版本：`research/fastpath-frontend/sign-core.js` + `research/fastpath-frontend/sign-worker.js`（端侧 VAD + DTW）与 `realtime/server.py`（慢路径造句/TTS）。
> 目标：**用真人数据回答一个问题——这套零训练方案在比赛/上线现场准不准、快不快。**

---

## 1. 验收指标（全部门禁，缺一不可）

| # | 指标 | 定义 | 门禁（P95/比例） | 采集方式 |
|---|---|---|---|---|
| G1 | L1 词元延迟 | 手停止移动 → 词上屏 | **≤ 250ms** | 页面 HUD / CSV `e2e_ms` |
| G2 | L2 词级语音 | 手停止移动 → 该词出声 | **≤ 450ms** | HUD + 人工秒表抽检 |
| G3 | 同人 Top-1 | 用本人 2 遍模板，测本人 10 次 | **≥ 80%** | CSV `expected == text` |
| G4 | 跨人 Top-1 | 用 A 的模板，测 B/C | **≥ 70%**（保底，不达标见 `6） | 跨人测试场次 |
| G5 | Top-3 命中 | 正确词出现在返回的 3 个候选里 | **≥ 95%** | CSV `topk` 列 |
| G6 | 拒识率 | 明显不匹配时应拒识而不是乱给 | ≤ 8% 的错误接受 | 人工复核 |
| G7 | 医疗词零编造 | 造句/语音不得添加词表外事实 | **0 例** | 人工复核 100 句 |

> 说明：G1/G2 是 0.5s 需求的落点；G3–G5 决定"能不能上线"；G7 是合规红线。

---

## 2. 测试环境（固定，不接受"我电脑上还行"）

- 浏览器：Chrome / Edge 120+
- 设备：i5-11 代或同级、核显；摄像头 1280×720@30fps
- 光照：室内正常白光；背景不要求纯色（骨骼方案的优势要测出来）
- 网络：同城宽带，RTT ≤ 30ms（端侧匹配不依赖网络，但造句/TTS 依赖）
- 页面：`python -m http.server 5173 --directory research/fastpath-frontend` + 后端 `uvicorn realtime.server:app --port 8000`

---

## 3. 测试集设计（50 词 × 3 人 × 10 次）

| 阶段 | 内容 | 时长 |
|---|---|---|
| 词表 | 取 hospital 场景 50 词（原 20 词 + `agentlayer/tools.py` 的 `W1_EXTRA_WORDS` 30 词），动作描述见 `backend/data/scenes.json` | 0.5 天 |
| 模板录制 | 每名签手语者每词录 **2 遍**（填模板名 → 点"录一个词" → 做一次动作；空格快捷键） | 每人约 20 分钟 |
| 测试 | 每名签手语者每词打 **10 次**（与模板不重复）；每次前在"期望词"输入框填该词 | 每人约 30 分钟 |
| 跨人 | 用 A 的**同一台机器、同一浏览器**（模板存在 IndexedDB，页面无导出功能，换机需重录），测 B、C | 每人 10 分钟 |

**注意**：模板与测试样本必须分开录，否则 G3 会虚高。

---

## 4. 操作步骤（每场测试）

1. 打开页面，选场景，确认 HUD 中 `模板` 数量正确（50 词 × 2 = 100）。
2. 清空日志与 CSV 记录（刷新页面即可清空 `evalRows`）。
3. 填写"期望词" → 打手语 → 等"词确认"日志出现 → 换下一个词。
4. 全部打完后点 **导出评估 CSV**，文件名带时间戳。
5. 把多人 CSV 放进 `reports/eval/`，运行汇总：

```bash
python scripts/summarize_eval.py reports/eval/*.csv
# 输出：Top-1 / Top-3 / P50/P95 延迟 / 每词错误分布，并写入 reports/eval_summary.md
```

6. 抽查 100 句字幕，人工复核 G7（编造/漏义）。

---

## 5. CSV 字段

| 字段 | 含义 |
|---|---|
| `ts` | 识别时间 |
| `expected` | 期望词（人工填写；跨人测试时也填） |
| `text` | 识别 Top-1 |
| `score` | 置信度（0–1） |
| `vad_ms` | 判停去抖耗时（固定成本，约 200ms） |
| `match_ms` | 端侧 DTW 匹配耗时 |
| `e2e_ms` | 端侧 L1 端到端 |
| `topk` | Top-3 候选（用竖线分隔） |

---

## 6. 不达标时的处理顺序（不要一上来就调阈值）

1. **先看错误分布**：是"同义近词混淆"（如 头疼/头/疼）还是"完全乱配"。
2. 同义近词混淆 → 调整词表（合并同义词）+ 在 `_SCENE_RULES` 里补模板句。
3. 完全乱配 → 检查模板质量（是否录了过渡帧、手出画面、光太暗），重录 2 遍。
4. 跨人掉点严重 → 每词增加模板到 3–5 人；仍不达标则启用备选方案：
   - 词表缩到 20–30 个高频词（比赛演示够用）；
   - 或切换到端侧小分类器（MindSpore Lite `.om` / ONNX，需采集训练，见架构文档 ADR-002 复议条件）。
5. 阈值：`startEnergy/stopEnergy` 在 Worker 通过 `config` 消息可调（默认 0.010/0.005），只在"切不出动作/切太碎"时动它。

## 8. 已知边界（写进报告，别藏）

- 本方案是**封闭词表**识别，不是开放词汇连续手语识别。
- 跨人泛化是最大风险，G4 是"能不能上线"的分水岭。
- 端侧匹配已不传视频、不传帧；但模板数据存在浏览器 IndexedDB，换设备需重录（或后续做云端模板同步）。
